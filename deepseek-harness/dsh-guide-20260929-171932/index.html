DeepSeek Harness 是怎么跑起来的

这份导览把 deepseek-harness（提交 4878cdab）拆成 10 个流程，每个流程一张图、一段讲解。图中每个方框都绑定了源码位置，点击节点可以跳到 GitHub 对应的行。建议按 ⓪→⑨ 的顺序阅读：⓪–② 讲“程序怎么启动”，③–⑨ 跟着用户的一条消息走完全程。

Harness（驾驭框架）包在大模型外面的那层程序：负责收消息、拼提示词、调模型、执行工具、记录历史。模型只负责“想”，harness 负责“做”。
Cordis / 插件底层框架。程序里的一切（模型适配、工具、日志、甚至 agent 循环本身）都是插件，通过 ctx 互相提供服务。
ctx.xxx 服务插件注册到上下文上的能力，比如 ctx.llm（调模型）、ctx.tools（工具）、ctx.sessions（日志）。
事件 / 瀑布（waterfall）插件之间的“钩子”。瀑布事件像一条链，每个监听者可以改写或拦截，然后调用 next() 交给下一个。
Turn / Step用户发一条消息 → 一个 Turn。Turn 里每“问一次模型 + 执行它要的工具”是一个 Step。
Session 日志只增不改的事件列表，是一切的事实来源：模型看到什么、UI 显示什么、重启后恢复什么，全从它推导。

⓪ 总览：系统里有哪些角色

一句话：一个 Node 进程里装着一棵插件树，浏览器通过 API 网关和它说话，Agent Loop 居中调度模型、工具和日志。

从左往右读主路径

  1. 用户在终端运行 dsh web，启动器组合 profile，Cordis Loader 挂载整棵插件树（上方一排）。
  2. 浏览器打开 127.0.0.1:3080，通过 HTTP / WebSocket 访问 API Gateway。
  3. Session Controller 找到或创建一个 Agent，把消息交给 Agent Loop。
  4. Agent Loop 向 System Prompt 要提示词，经 LLM 适配层 调 DeepSeek API。
  5. 模型要用工具时，经 工具注册表 → Bash + 沙箱 → 子进程执行；需要更高权限时先问用户。
  6. 每一步都写进 Session 日志，再由持久化插件写到磁盘上的 JSONL 文件。

在 harness 层面怎么体现

  • 没有“核心代码”可改：图里每个方框都是一个可替换的插件行，想换模型厂商就换 LLM 适配器，想换执行环境就换 shell / sandbox 提供者。
  • 大框（Host 进程）表示它们都在同一个进程、同一棵 Cordis 树里；小框（沙箱策略）表示真正执行命令的部分被文件写权限限制住。

① 启动流程：dsh web 如何把插件树跑起来

一句话：命令行只决定“用哪个 profile”，真正的程序是 Loader 按配置一行行挂载出来的插件。

按图从左到右

  1. 解析命令行：dsh web 被改写成 dsh --profile web；profile 是“要装哪些插件”的清单。
  2. .env 快照 + 代理：读取当前目录和 ~/.dsh 的 .env，冻结成只读快照，之后所有插件都从这份快照取环境变量。
  3. 加载 Profile 目录：~/.dsh/profiles/web 第一次使用时由内置模板生成，里面只写了 bundle 列表 [dsh-base, dsh-web-app]。
  4. 组合补丁层：把各层 cordis.patch.yml 按顺序排成一个数组（详见 ②）。
  5. boot()：创建根 Context，挂上 Loader，注入 profile 信息、环境快照、命令行参数等“宿主服务”。
  6. 逐行挂载插件：每行 import 对应的包，调用 ctx.plugin()。其中 webserver 行开始监听 3080 端口。
  7. 启动审计：确认 agent-loop、webserver、connection 等必需行都是 ACTIVE；否则写日志并以退出码 1 结束。
  8. 就绪：提交 appReady 后网关才开放 WebSocket；web-runtime 打印 URL 并打开浏览器。

在 harness 层面怎么体现

  • 启动器本身几乎不懂业务：它不认识“工具”或“模型”，只负责读配置、创建 Loader、做健康检查。
  • “应用是什么”完全由配置决定：web、headless、sdk 用的是同一个启动器，只是 bundle 不同。
  • 失败要大声：必需插件没起来就直接退出，而不是带病运行。
想看自己机器上最终挂载了哪些行：dsh --profile web --dump-config

② 配置层叠：YAML 补丁怎样变成插件树

一句话：五层 YAML 补丁从低到高依次叠加，得到最终的“行”列表，每一行就是一个插件实例。

五层补丁（越靠后优先级越高）

  1. dsh-base：公共底座，插入模型适配、工具、会话、沙箱、审批、遥测等核心行。
  2. dsh-web-app：加上 Web 服务器、前端静态资源、会话控制器和几个 agent 预设。
  3. profile 自己的 cordis.patch.yml。
  4. home 级 ~/.dsh/cordis.patch.yml：对所有 profile 生效的个人偏好。
  5. 命令行 --patch：临时覆盖，按参数顺序。

合并规则

  • 带 insert 的补丁追加新行；只带 id 的补丁找到同 id 的行，整键替换 config（不做深合并）。
  • 配置里的 !!js 表达式在挂载时求值，比如 port: ctx.webStartup.port ?? 3080。

在 harness 层面怎么体现

  • 这就是“一切皆插件”的落点：想换掉任何一个组件，写一行同 id 的补丁即可，不用改源码。
  • isolate 可以让某个服务只在特定“领域”可见，用来给不同 agent 预设不同的工具集。
例子：想把默认权限改成只读，在 ~/.dsh/cordis.patch.yml 里写一条 id: sandbox-policy 的补丁，把 config.mode 改为 read-only。注意是整键替换：原来 config 里的 workspaceRoot 也要一起写上。

③ 消息入口：从按下发送到 Agent 被唤醒

一句话：浏览器用 HTTP 把消息投递给会话控制器，控制器把它放进 Agent 的收件箱就立即返回；结果再通过 WebSocket 流推回来。

按时间从上往下

  1. 打开会话时，客户端先用 WebSocket 订阅 session.follow 流（后面的结果都从这里回来）。
  2. 按下回车 → session.prompt() → POST /api/session/prompt。
  3. Connection 做信任校验（Host/Origin + Cookie/token），通过后交给 Gateway 派发给 @Remote prompt()。
  4. 会话控制器找到 Agent：内存里有就直接用，没有就从磁盘恢复（resume）或新建（create）。
  5. agent.followup(message)：消息进入 inbox 的 next-turn 队列，写一条 agent/inbox/spliced 事件。
  6. HTTP 立刻返回 {accepted: true}——浏览器不等这轮对话结束。
  7. Agent 被唤醒开始工作（④⑤），产生的日志事件和实时文字流经 follow 流推回浏览器。

在 harness 层面怎么体现

  • “收消息”和“处理消息”彻底解耦：控制器只负责投递，处理由 Agent 的驱动循环异步完成。
  • inbox 的内容由日志事件折叠而来，进程重启后还能恢复排队中的消息。
  • 以 / 开头的斜杠命令走另一条路：commands.execute 直接写日志并执行，不唤醒模型。
  • headless 模式没有网关：直接在进程内 agents.create + followup，再 whenIdle() 等结束。

④ Agent 状态机：一个 Agent 从创建到释放

一句话：Agent 只有 idle / maintenance / running 三种内部阶段；有消息就进入 running，一个接一个跑 turn，跑空了回到 idle。

主路径

  1. 已创建：agents.create 或 resume 构造出 Agent。
  2. maintenance：执行 setup（安装模型选择、挂载预设），并串行通知所有 agent/created 监听者。期间收到的消息会被“锁存”，初始化完再补唤醒。
  3. idle：等待消息。
  4. running：wakeDriver() 创建一个 AbortController，开始 while (await turn()) 循环。
  5. turn/end：每个 turn 结束时，如果 inbox 里还有消息就换一个新的 AbortController 接着跑下一 turn，否则回到 idle。

三种投递方式

  • followup：放进 next-turn 并唤醒（普通发送）。
  • steer：放进 next-step 并唤醒（在当前 turn 里“插一句”）。
  • inject：放进 next-step 但不唤醒（插件补充上下文）。

在 harness 层面怎么体现

  • 出错不是一种状态：发 agent/error 后回到 idle，turn/end 里记录原因。
  • 取消（cancel）只是触发 abort 信号，驱动在 finally 里自己退回 idle，避免状态被外部硬改。

⑤ Turn / Step 循环：Agent 一轮工作的完整流程

一句话：认领消息 → 组装请求 → 问模型 → 执行工具 → 如果模型还需要再看工具结果就再来一步，否则结束这一轮。这是整个 harness 的心脏。

四条泳道各管什么

  • Inbox：等待处理的消息（next-turn / next-step 两个队列）。
  • 插件扩展点：循环在固定位置抛出事件，插件可以在这里改写、拦截、重试。
  • Agent Loop 驱动：真正的执行顺序。
  • Session 日志：每一步产生的“事实”。

一个 Step 的顺序

  1. 认领：拿走 next-step 全部 + next-turn 一条；组装提示词、工具 schema、运行时上下文。
  2. agent/pre-step：插件决定 enter（可改写消息）或 reject（整轮 blocked）。
  3. agent/request 选模型 → prepareCall → 把 system/user/request 事件写进日志。
  4. 从日志派生并冻结请求，流式调用模型，写 assistant/message。
  5. 有 tool-call 就执行工具，写 tool/call、tool/result。
  6. step/end：执行过工具 → 进入下一 Step；否则触发 agent/turn-stopping，写 turn/end。

在 harness 层面怎么体现

  • 循环本身很“薄”：它只规定顺序和写日志，所有策略（改写输入、换模型、重试、压缩、续命）都挂在扩展点上。
  • 项目规则写明：新功能应该挂到扩展点上，而不是改 agent-loop；真要改循环，必须同步更新架构文档。
  • 瀑布监听者必须调用 next()，否则后面的插件和默认行为都会被短路。
turn/end 的原因：completed（模型不再调工具）、max-tokens（输出被截断，不执行工具）、blocked（pre-step 拒绝）、aborted（被取消）、error（异常且不重试）。

⑥ 请求组装：模型看到的内容从哪里来

一句话：提示词、工具、上下文、用户消息先写进日志，真正发给模型的 messages 再从日志“派生”出来——所以日志永远能还原模型看到了什么。

数据怎么流

  1. 各插件用 systemPrompt.section() 贡献提示词段落，按 order 数字排序（harness 身份 -1000 排最前），再做 {{变量}} 插值。
  2. 工具注册表只把 name / description / parameters 交给提示词组装。
  3. 沙箱模式、审批策略等“当前状态”变成一条 runtime-context 用户消息，内容变化时才重发。
  4. 这些内容经过 agent/pre-step 决策后，以 system/message、user/message、request/header 等事件写入日志。
  5. deriveMessages() 按 Surface 上的节点顺序把事件变成消息，冻结后作为请求发出。

在 harness 层面怎么体现

  • 核心约束“模型可见 ⟺ 已记录”：任何想让模型看到的新内容，都必须先成为一条日志事件。
  • agent-loop 在 llm/stream 最前面挂了一个不变量检查：请求 messages 必须和日志派生结果逐字相同，系统提示必须是日志第 0 个节点。
  • 好处：恢复会话、分叉、导出、遥测都只需要读日志，不会出现“模型看到的”和“记录的”不一致。

⑦ 一次模型调用：从 prepareCall 到流式结果

一句话：ctx.llm 是一个接口，DeepSeek 适配器是它的一个实现；请求穿过 llm/stream 插件链后，被翻译成 Anthropic Messages 格式发往 DeepSeek，流式结果再翻译回统一格式。

按时间从上往下

  1. 准备：prepareCall(config) 找到对应 provider 的适配器，取模型信息，补全默认 maxTokens / reasoningEffort，返回只能使用一次的 stream()。
  2. 发送：stream(request) 先经过 llm/stream 瀑布（一致性校验、把会话落盘），最后到适配器。
  3. 适配器序列化消息，POST {baseURL}/v1/messages（默认 https://api.deepseek.com/anthropic），用 x-api-key 认证，接收 SSE。
  4. SSE 事件被翻译成 7 种 StreamChunk：block-start、text-delta、reasoning-delta、tool-call-delta、block-end、usage、finish。
  5. 每个 chunk 立刻作为实时帧推给 UI；流结束后一次性写入 assistant/message。
  6. 失败：写 assistant/attempt（只进日志、不进模型历史），发 agent/request-error；llm-retry 决定是否退避重试。

在 harness 层面怎么体现

  • 换模型厂商 = 注册另一个适配器（pi-ai 适配器就支持 OpenAI、Anthropic 等），循环代码一行不动。
  • 重试不写死在适配器里，而是作为插件挂在 agent/request-error 上，策略可配置。
  • 默认可重试：RATE_LIMIT、SERVER、TIMEOUT、TRANSPORT、EMPTY_RESPONSE，最多 5 次，0.5s 起翻倍、封顶 10s；有 retry-after 就优先用它。

⑧ 工具执行管线：一次 bash 调用经过的每一关

一句话：模型说“我要运行这条命令”后，调用要依次经过准备、放行判断（可能要问用户）、执行（套进沙箱）、收尾（超长输出存文件），最后结果按顺序写回日志。

按列从左到右

  1. 分组 + tool/call：声明 isConcurrencySafe 的工具（如 read）可以并行，bash / write / edit 独占执行；先写一条 tool/call。
  2. createExecution：把参数冻结成快照。
  3. tools/pre-execute：插件返回 allow / deny / ask / cancel。ask 会交给 ctx.approval，在浏览器弹出审批卡片。
  4. tools/execute：外层包装加超时、先把会话落盘，再调用工具本体。
  5. bash 本体：校验参数、解析沙箱策略；用 sandbox-exec（macOS）或 bwrap/Landlock（Linux）包住命令，再启动子进程，输出有上限，完整内容另存文件。
  6. tools/post-execute：spill-policy 把超过 12500 token 的输出换成预览 + 文件位置；repeat-tool-reminder 提醒重复调用。
  7. 提交 tool/result：按模型给出的顺序写回日志。

在 harness 层面怎么体现

  • 工具是“接缝”的消费方：bash 工具只调用 ctx.shell，而 shell 的实现（本地 / 沙箱 / 远程）可以整体替换。
  • 安全是分层的：放行判断（hooks、审批）+ 执行隔离（沙箱只限制写文件，不限制网络）+ 权限升级需要再次审批。
  • 默认 workspace-write：只能写工作区；DSH_PERMISSION_MODE=danger-full-access 会关掉沙箱并把审批策略设为 never。
  • 被拒绝的调用也会生成一条 isError 结果，模型能看到“为什么被拒”。

⑨ Session 日志：一条事件写下之后去了哪里

一句话：session.append() 写下的每条事件会同时流向三处：磁盘（持久化）、浏览器（给人看）、下一次模型请求（给模型看）。

三个去向

  1. 落盘：JSONL 插件监听 session/event，缓冲 200ms 批量追加并 fsync；模型调用前、工具派发前还会强制 flush。
  2. 给人看：投影（projection）把事件折叠成状态（inbox、turn 边界、标题…），follow 流把快照 + 增量推给浏览器。
  3. 给模型看：Surface 只保留 system / developer / user / assistant / tool 五类节点，deriveMessages() 把它们变成下一次请求。

重启之后

  • 文件在 ~/.dsh/.../<会话>/session.v4.jsonl；旧版本文件按 v0→v4 逐级迁移，新版本另存，绝不覆盖旧文件。
  • resume：读回全部事件，给中断的 turn 补上结束事件，再作为种子重建 Agent。fork：复制到某个 turn 边界的事件作为新会话的种子。

在 harness 层面怎么体现

  • 事件溯源（event sourcing）：状态不是存出来的，而是从事件“算”出来的，所以 UI、模型、磁盘三者天然一致。
  • “修改历史”也是追加：上下文压缩写一条 replace 事件，在 Surface 上把一段旧节点替换成摘要，原始事件仍在日志里；UI 仍显示用户当初看到的内容。
  • 持久化是插件：实现 SessionPersistence 接口（create / open / stat / list）就能换存储后端。
