## 1. 一句话理解

**Hermes 是一个"会动手的 AI 助理"。** 普通聊天机器人只会回答文字；Hermes 除了回答，还能自己**跑命令、读写文件、上网搜索、操作浏览器**，并且会**记住你**，越用越顺手。

打个比方：

| 现实中的角色 | Hermes 里对应的部分 |
|---|---|
| 你（老板） | 用户 |
| 前台 / 电话 / 微信 | 各种入口：命令行、桌面 App、Telegram 等聊天软件 |
| 助理本人的"大脑回路" | `AIAgent` 智能体核心 |
| 助理请教的专家顾问 | 大模型（OpenAI、Anthropic 等） |
| 助理手边的工具箱 | 工具系统（终端、文件、网页、浏览器……） |
| 助理干活的工位 | 执行环境（本机、Docker、SSH 远程机……） |
| 助理的笔记本 | 记忆与技能（MEMORY.md、USER.md、skills/） |
| 聊天记录档案柜 | 会话数据库 state.db（SQLite） |

## 2. 整体架构：几个大块

对照架构图，从左到右看：

### ① 入口：你从哪里找它
- **CLI / TUI / 桌面 App**：在终端输入 `hermes`，或打开桌面程序。
- **消息网关（gateway/）**：让 Hermes 挂在 Telegram、Discord、Slack、微信等 20 多个平台上。每个平台有一个"适配器"，负责把各家不同格式的消息翻译成统一的 `MessageEvent`。
- **定时任务（cron/）**：你可以预约"每天早上 9 点帮我总结新闻"，时间到了调度器自动叫醒智能体。
- 此外还有 IDE 插件（ACP）、批量任务等入口。

**关键点：所有入口最后都创建同一个 `AIAgent`。** 这就是为什么在命令行和在 Telegram 里，Hermes 的能力是一样的。

### ② 大脑：AIAgent（`run_agent.py` + `agent/`）
这是整个项目的核心。它做的事情可以概括成一个循环：

```
想一想（问大模型）→ 需要动手吗？
   ├─ 需要：调用工具 → 拿到结果 → 再想一想……
   └─ 不需要：把答案交给用户，结束
```

代码里这个循环在 `agent/conversation_loop.py` 的 `while` 里，每一步（组装请求、调模型、处理错误、执行工具、压缩上下文……）都拆成一个单独的 `agent/turn_*.py` 文件，方便维护。循环次数有上限（CLI 配置 `max_turns` 默认 500），防止失控。

### ③ 顾问：大模型提供方
Hermes 本身不"思考"，思考交给大模型。它支持很多家服务商，`agent/transports/` 里为每家写了适配代码，对上层统一成同一种消息格式（OpenAI 风格的 `system / user / assistant / tool` 消息）。

### ④ 工具箱：工具系统（`model_tools.py` + `tools/`）
- 每个工具（如 `terminal`、`read_file`、`web_search`）写在 `tools/*.py` 里，文件被导入时**自己注册**到 `tools/registry.py` 的注册表。
- 大模型说"我要调用 read_file"，`handle_function_call()` 就去注册表查到对应的函数执行，再把结果以 JSON 字符串返回。
- 工具按"工具集（toolset）"分组，可以按需开关。
- 少数和智能体自身相关的工具（`memory`、`todo`、`delegate_task` 等）由智能体直接内联处理。

### ⑤ 工位：执行环境（`tools/environments/`）
`terminal` 工具跑的命令不一定在你电脑上执行——可以放进 Docker 容器、SSH 远程主机、Modal/Daytona 云沙箱里，更安全也更灵活。

### ⑥ 笔记本和档案柜
- **记忆与技能**：`memory` 工具把重要信息写进 `MEMORY.md`（助理自己的笔记）和 `USER.md`（关于你的画像）；技能（skills）是一份份"操作手册"。**下次开新会话时**，它们会被读进系统提示词。
- **会话数据库 `state.db`**：每一轮对话的消息都会追加写入 SQLite，下次继续聊时从这里读出历史；还支持全文搜索过去的对话。

### ⑦ 扩展：插件（`plugins/`）
聊天平台、模型提供方、记忆后端、图片生成等，大多以插件形式接入。项目的设计原则是：**核心保持精简，新能力尽量放到边缘（插件、技能、命令行子命令）**。

## 3. 数据流：一条消息的完整旅程

对照数据流图，以"在 Telegram 里问一句话"为例：

1. **输入**：你发送"帮我看看服务器磁盘还剩多少"。
2. **接入**：Telegram 适配器收到消息 → 网关 `_handle_message` 做鉴权（你有没有权限）、找到你的会话、判断是不是 `/xxx` 斜杠命令。同时从 `state.db` 读出这个会话之前的聊天记录。
3. **组装请求**：把三样东西拼在一起：
   - **系统提示词**：Hermes 的身份说明 + 项目里的 `AGENTS.md` + 你的记忆 + 技能目录；
   - **历史对话**；
   - **你这次的消息**；
   再附上"可用工具清单"。
4. **推理**：发给大模型。模型可能有两种回应：
   - **要用工具**（返回 `tool_calls`）：比如"执行 `df -h`"。Hermes 通过工具系统在执行环境里跑命令，把输出作为 `tool` 消息放回对话，**回到第 3 步再问一次模型**。这个"想→做→再想"的回路可以转很多圈。
   - **直接给答案**：模型输出最终文字。
5. **输出与保存**：最终文字通过适配器的 `send` 发回 Telegram；这一轮产生的所有消息（助手回复、工具调用和结果）写入 `state.db`。

## 4. 两条值得记住的"铁律"

### 铁律一：系统提示词整场对话不变
系统提示词在会话开始时构建一次，之后**一个字节都不改**。原因是大模型服务商会缓存"不变的开头部分"，下一轮只需为新增内容付费——改了开头，缓存全部失效，费用和延迟都会成倍上升。

所以：
- 你让它记住的新内容会立刻写进 `MEMORY.md`，但要**下次新会话**才出现在提示词里；
- 很多改动提示词的命令默认"下次生效"，需要立刻生效时才加 `--now`。
- 唯一的例外是**上下文压缩**：对话太长快塞不下时，会把旧内容总结成摘要，这时才重建。

### 铁律二：核心要窄，能力放在边缘
每个工具的说明书都会随每次请求发给模型，工具越多越贵、越容易让模型分心。所以新功能优先做成插件、技能或命令行子命令，而不是往核心里加工具。

## 5. 想读源码，从哪开始？

| 想了解 | 先看 |
|---|---|
| 智能体主循环 | `agent/conversation_loop.py`（`run_conversation` 和其中的 `while`） |
| 系统提示词怎么拼 | `agent/system_prompt.py` → `build_system_prompt_parts` |
| 工具怎么被调用 | `model_tools.py` → `handle_function_call`；`tools/registry.py` |
| 写一个新工具 | `tools/file_tools.py` 末尾的 `registry.register(...)` 示例 |
| 聊天平台怎么接入 | `gateway/platforms/base.py`、`gateway/platforms/ADDING_A_PLATFORM.md` |
| 会话怎么存 | `hermes_state.py`（`SessionDB`） |
| 各模块的开发规范 | 各目录下的 `AGENTS.md` |
