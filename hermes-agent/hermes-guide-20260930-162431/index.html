00 · 先看这里

Hermes 是一个“会动手的 AI 助理”：不仅能聊天，还能自己跑命令、读写文件、上网、操作浏览器，并且会记住你。

打个比方：Hermes 像一位私人助理。大模型是它请教的专家顾问，工具是它手边的工具箱，执行环境是它干活的工位，记忆文件是它的笔记本，state.db 是聊天档案柜。

建议阅读顺序

  1. 01–02：先建立全局印象，知道有哪些部分、一条消息怎么走完全程。
  2. 03–06：钻进 Agent 内部，看它怎么启动、怎么准备提示词、怎么循环、怎么调用工具。
  3. 07：看聊天平台（Telegram 等）怎么接进来。
  4. 08–10：进阶话题：出错了怎么办、对话太长怎么办、怎么越用越聪明。

01 · 整体架构：Hermes 由哪几块组成

一句话：多个入口 → 同一个 AIAgent 大脑 → 大模型负责思考、工具负责动手、数据库和记忆负责“记住”。

按图走一遍

  1. 用户可以从三类入口进来：CLI / TUI / 桌面（在电脑上直接用）、消息网关（在 Telegram、Discord、Slack 等 20 多个平台里聊天）、定时任务（预约好的任务到点自动运行）。
  2. 不管从哪个入口进来，最后都会创建同一个 AIAgent。所以各个入口的能力完全一样。
  3. AIAgent 在会话开始时读取记忆与技能，放进“系统提示词”。
  4. 它把对话发给大模型提供方（OpenAI、Anthropic 等），拿回答复。
  5. 如果大模型说“我要用工具”，AIAgent 就交给工具系统，工具可能在执行环境（本机、Docker、SSH 远程机）里跑 shell 命令。
  6. 每一条消息都会写进会话数据库 state.db，下次可以接着聊。
设计原则：核心要“窄”。每个工具的说明都会随每次请求发给模型，越多越贵，所以新能力优先做成插件、技能或命令行子命令。

02 · 一条消息的旅程

一句话：消息进来 → 拼上提示词和历史 → 问模型 → 要么直接回答，要么“用工具→再问模型”直到能回答 → 回复并存档。

按图走一遍（以 Telegram 为例）

  1. 用户消息：你发了“帮我看看服务器磁盘还剩多少”。
  2. 网关入口：检查你有没有权限、找到你的会话、判断是不是 /命令。同时从 state.db 读出历史记录。
  3. 请求组装：把系统提示词（system 消息）+ 过往对话 + 你这句话（user 消息）+ 可用工具清单拼在一起。
  4. 大模型回应。如果它返回 tool_calls（比如“执行 df -h”），就进入工具执行，结果作为 tool 消息回到请求组装，再问一次模型。这个回路可以转很多圈。
  5. 当模型不再要工具、直接给出文字时，回复用户；这一轮的所有消息写入会话数据库。

03 · AIAgent 启动：构造时做了哪些准备

一句话：AIAgent(...) 被创建时，先“连上大模型”，再“装配能力与状态”。系统提示词此时还没拼。

按图走一遍（图中是一条 S 形路线）

  1. AIAgent(...)：调用方传入模型名、API 密钥、平台（cli / telegram…）、会话 ID 等参数。__init__ 本身只做转交，真正的工作在 agent/agent_init.py::init_agent。
  2. 预算与模式：创建迭代预算（限制最多循环几次），并判断和这个服务商用哪种通信协议（api_mode，如 chat_completions、anthropic_messages）。
  3. 确定路由：规范化模型名；如果传入的凭据池和服务商不匹配就丢弃。
  4. 创建客户端：按协议创建对应的 SDK 客户端（OpenAI、Anthropic、Bedrock…）。
  5. 备用模型链：准备好“主模型挂了换谁”的列表。
  6. 加载工具清单：从工具注册表里挑出这次允许用的工具。工具按“工具集（toolset）”分组，环境不满足的工具（check_fn 不通过）会被隐藏，模型根本看不到。
  7. 会话状态：确定 session_id，绑定 state.db，创建待办列表等。
  8. 载入记忆：从磁盘读 MEMORY.md / USER.md；如果配置了外部记忆插件（如 mem0、honcho）也一并加载。
  9. 上下文引擎：创建负责“对话太长就压缩”的 ContextCompressor。
  10. Agent 就绪：此时系统提示词仍为空，要等第一次对话时才构建（见 04）。
在消息网关里，构造好的 AIAgent 会按会话缓存复用，而不是每条消息都重新初始化——这样既快，又能保证提示词缓存有效。

04 · 系统提示词是怎么拼出来的

一句话：把“身份 / 项目规则 / 记忆技能”分三层拼成一段文字，首轮构建后整场对话一个字都不改。

什么是系统提示词？

每次请求模型时，消息列表的第一条是 system 消息，告诉模型“你是谁、要遵守什么、用户是什么样的人、有哪些技能可用”。它就是系统提示词。

按图走一遍

  1. 身份与守则（来自 SOUL.md 或内置默认身份，外加工具使用指南）→ 放进稳定层 stable。
  2. 项目说明文件：在当前目录找 .hermes.md → AGENTS.md → CLAUDE.md → .cursorrules，只加载找到的第一种 → 放进上下文层 context。
  3. 记忆与技能：MEMORY.md / USER.md 的“开局快照”和技能目录摘要，再加上日期、会话 ID、运行环境提示 → 放进易变层 volatile。
  4. 三层按顺序拼成一段文本（build_system_prompt）。
  5. 首轮：结果放进内存缓存 _cached_system_prompt，同时存档到 state.db 的会话行里。
  6. 续聊（比如网关重启后）：如果模型、服务商、工作目录都没变，就从 state.db 原样恢复旧文本，而不是重新拼。
  7. 之后每一轮请求，都把这段文字原样作为第一条 system 消息发出去。
为什么要“一字不改”？模型服务商会缓存请求开头相同的部分，下次只为新增内容全价付费。开头一变，缓存就全部失效，费用和延迟成倍上升。所以越稳定的内容放越前面；对话中途新写的记忆，也要等下次重建才出现在提示词里。唯一允许重建的时机是上下文压缩（见 09），以及 CLI 执行 /new 等重置操作。

05 · 一个回合内部：Agent 主循环（最核心）

一句话：用户说一句话 = 一个“回合”；一个回合里可能请求模型很多次，每次叫一“轮迭代”。有工具调用就继续转，没有就结束。

回合 vs 迭代：你让助理“查一下磁盘并清理日志”，这是一个回合；助理先查磁盘、再列日志、再删除、最后汇报，每一步都要问一次顾问，这是多轮迭代。

① 回合开始（只做一次）

  1. 拿会话锁：保证同一个会话不会同时跑两个回合（比如你连发两条消息）。回合结束时在 finally 里释放。
  2. 准备上下文：把你的消息加进对话；如果系统提示词还没构建就构建（见 04）；对话已经很长就先压缩；然后先把你的消息写进 state.db——即使后面崩溃，你说过的话也不会丢。

② 每次迭代：准备并请求模型

  1. 开始本轮：检查是否被打断（比如你发了 /stop）、预算是否用完；都没问题就扣一次预算。若需要停，走向提前停止。
  2. 组装请求：把消息整理成要发给 API 的格式，处理插话（/steer）、修正角色顺序，并插入缓存断点。
  3. 长度检查：估算长度，快超出模型窗口就先压缩再继续。
  4. 调用大模型：默认流式请求——模型一边生成，文字就一边推给界面；遇到网络、限流等错误会自动重试（详见 08）。

③ 看模型怎么回

  1. 解析回复：把各家不同格式的返回统一成一条 assistant 消息，看里面有没有 tool_calls。
  2. 有 → 执行工具：先把这条 assistant 消息存库，再执行工具，每个结果作为 tool 消息追加到对话；然后沿虚线“下一轮”回到“开始本轮”。
  3. 没有 → 文字答复：这就是最终答案。如果模型返回了空内容，会尝试补救（提示它继续、重试等）；然后存库并跳出循环。

④ 收尾

  1. 收尾整理：如果预算用完还没答案，会额外请求一次让模型做个总结；然后持久化会话、同步外部记忆；必要时在后台启动“复盘”（见 10）。
  2. 返回结果：返回一个字典，里面有 final_response（最终回答）、messages（完整消息列表）、调用次数、是否被打断等。
代码组织：循环本体在 agent/conversation_loop.py 的 while（约 1636 行）里，每个阶段是一个独立的 agent/turn_*.py 文件。想改“某一步”，只需要找对应的那个文件。

06 · 一次工具调用的全过程

一句话：模型说“调用 terminal 执行某命令” → 层层检查 → 真正执行 → 结果包装成一条 tool 消息回到对话。

这是一张“时序图”，怎么看？

顶部每个方块是一个参与者，向下的虚线是它的时间线；横向箭头表示“谁调用谁”，从上往下按时间顺序读。实线是调用，灰色虚线是返回。

① 分发

  1. 主循环 → 执行器：先校验（工具名写错会尝试自动修正、参数必须是合法 JSON），把 assistant 消息存库后才开始执行。多个只读工具（读文件、搜索网页等）可以并行，最多 8 个同时跑；写文件这类操作按顺序执行。
  2. 执行器 → 插件钩子：插件的 pre_tool_call 钩子可以放行、改参数、拦截，或要求人工审批。
  3. 执行器 → 分发入口：memory、todo、delegate_task 这类“内联工具”由 Agent 自己处理；其余工具交给 handle_function_call。
  4. 分发入口 → 注册表：registry.dispatch 根据工具名找到处理函数（每个工具在 tools/*.py 里用 registry.register(...) 自己登记）。

② 执行（以 terminal 为例）

  1. 危险命令审批：像 rm -rf 这样的危险命令，会先弹出审批，经你同意才执行。
  2. 执行环境：命令在配置好的环境里执行——本机、Docker 容器、SSH 远程主机或云沙箱；同一个任务会复用同一个环境。

③ 结果回流

  1. 结果一律是 JSON 字符串；就算工具报错，也会被包装成错误 JSON，不会让循环崩溃。
  2. post_tool_call 钩子可以观察结果；结果太长（约 10 万字符）会写进文件、只留预览；工具第一次进入某个目录时，如果那里有 AGENTS.md，会把它附在结果后面，帮模型了解这个目录的规矩。
  3. 最终变成一条 role: "tool" 的消息，追加到对话并存库。
子智能体：delegate_task 会新建一个“子 AIAgent”去完成子任务。它继承父亲的模型、凭据和工具集，但不读项目文件、不带记忆，有自己的系统提示词和预算，完成后把结果交回父亲。

07 · 消息网关：一条 Telegram 消息的处理

一句话：平台适配器把各家消息统一格式 → 网关检查权限和会话 → 在后台线程运行 AIAgent → 一边生成一边编辑 Telegram 消息 → 存档。

① 接收与准备

  1. 平台适配器用长轮询收到消息。Telegram 会把很长的粘贴拆成几条，适配器会先等一会、合并成一个 MessageEvent。
  2. 网关入口依次检查：你是否被授权（陌生人私聊会收到一个配对码）、是否紧急停止、是不是斜杠命令。
  3. 如果这个会话正在忙（上一条还没处理完），新消息默认会打断当前回合；也可以配置为排队或“插话”（steer，悄悄塞给正在运行的回合）。
  4. 从会话存储取出会话并读取历史记录。

② 运行 Agent

  1. 回合执行：在线程池里运行，并绑定这条消息所属的 profile（一个网关可以服务多个账号，彼此隔离）。
  2. 按会话查 AIAgent 缓存：配置没变就复用，否则新建。然后调用 run_conversation（就是 05 讲的主循环）。
  3. 模型每生成一段文字，流式推送组件就去编辑同一条 Telegram 消息，你会看到回答一点点“长出来”。

③ 收尾与回复

  1. AIAgent 已经在循环中逐步写库；网关结束后再“补写”一次，已写过的行会跳过，不会重复。
  2. 如果已经流式发完，就只补发图片和页脚；否则由适配器发送最终文本。
  3. 对话接近上下文上限的 85% 时，网关会在下个回合开始前先压缩一次（“会话卫生”），比 Agent 自己的阈值更高，作为兜底。

08 · 调用模型出错了怎么办

一句话：先判断是什么错，再对症下药——等一等、换密钥、压缩、换模型，实在不行才报错。

按图走一遍

  1. 请求模型时出错，进入错误分类：根据 HTTP 状态码、错误码、错误文字判断原因，并给出四个建议——能否重试、要不要换密钥、要不要压缩、要不要换模型。
  2. 超时 / 过载 / 服务端错误 → 等一会再试：等待时间从 2 秒起、逐渐加长（最长 60 秒）；服务端告诉了 Retry-After 就听它的。默认最多重试 3 次。
  3. 限流 / 欠费 / 401 未授权 → 换一个密钥：如果配置了多个 API Key（凭据池），就换下一个；401 会先尝试刷新令牌。
  4. 上下文超长 → 压缩上下文：采用服务商报告的真实上限，压缩后重来，最多 3 次；压不动了就以错误结束。
  5. 以上成功后都会重新请求，回到主循环。
  6. 403、模型不存在等不可重试的错误，以及重试用尽、密钥换完时 → 切换备用模型（按配置的 fallback 链）。
  7. 没有备用模型可用 → 结束并报错，告诉用户原因。
临时故障还有一道“自动恢复阶梯”：只要还没向用户输出任何文字，会再按 15 / 30 / 60 秒等待重试几次，尽量不让用户看到错误。

09 · 上下文压缩：对话太长时怎么办

一句话：模型一次能读的文字有上限（上下文窗口），对话太长就把中间部分总结成摘要，保留开头和最近几轮。

① 什么时候触发

  • 自动：每次请求模型前、工具结果回来后检查，超过阈值（默认窗口的 50%；窗口小于 512K 的模型至少 75%）就压缩。
  • 服务商报超长：请求被拒说“太长了”，也会压缩后重试。
  • 手动：用户输入 /compress。

② 压缩四步

  1. 裁剪旧工具输出：很早以前的命令输出、文件内容先剪短——不调用模型，几乎零成本。
  2. 划定范围：保护开头几条（默认 3 条）和最近一段对话，只处理中间部分。
  3. 生成摘要：用“辅助模型”把中间部分写成结构化摘要。
  4. 摘要生成失败时，用规则拼一个兜底摘要（不调模型），保证流程能走完。

③ 压缩之后

  1. 拼回对话：开头 + 摘要 + 结尾，并修复被切断的“工具调用—结果”配对，保证消息格式合法。
  2. 重建系统提示词：这是整个系统里唯一允许的“缓存重置”时机。
  3. 旧消息归档：默认原地压缩，旧消息软归档，会话 ID 保持不变。

10 · 记忆与学习：Hermes 如何越用越懂你

一句话：对话中主动记笔记、对话后后台复盘，把经验存成“记忆”和“技能”，下次会话开局读进来。

按图走一遍

  1. 当前对话中，模型觉得某件事值得记（比如“用户喜欢用 pnpm”），就调用 memory 工具（add / replace / remove）。
  2. memory 工具立即写盘到记忆文件：MEMORY.md 是 Agent 给自己的笔记，USER.md 是关于你的画像。它们都有字数上限（约 2200 / 1375 字符），逼它只记要点。
  3. 每 10 轮左右，回答发出之后，会启动一个后台复盘：复制一个“分身 Agent”，在后台线程里回看刚才的对话，判断有没有值得补记的记忆、有没有值得新建或修补的技能。整个过程不打扰主对话。
  4. 技能库里每个技能是一份 SKILL.md 操作手册。技能管家（curator）会定期把长期不用的技能归档（14 天标记过期、30 天归档；只归档不删除，被固定的技能除外）。
  5. 下一次会话开始时，记忆文件的快照和技能索引被读进系统提示词——Agent 就“记得”你了。
补充：session_search 工具可以在 state.db 里全文搜索过去的对话（不调用模型）；还可以接入 mem0、honcho 等外部记忆插件，它们会在每轮请求前预取相关记忆、每轮结束后同步。

11 · 名词小词典

名词通俗解释
大模型 / LLM负责“思考”的 AI 服务，如 GPT、Claude。Hermes 自己不思考，只负责组织对话和执行动作。
Token模型计量文字的单位，大约 1 个汉字 ≈ 1–2 个 token。费用和上下文上限都按 token 算。
上下文窗口模型一次最多能读多少 token。对话超过它就必须压缩。
系统提示词每次请求的第一条消息，告诉模型它是谁、要守什么规矩。
提示词缓存服务商对“请求开头相同的部分”打折复用。Hermes 的很多设计都是为了不破坏它。
tool_calls模型回复里“我要调用某个工具、参数是什么”的结构化请求。
工具 / 工具集工具是 Agent 能执行的动作（terminal、read_file…）；工具集（toolset）是一组工具，可整体开关。
回合 / 迭代用户说一句话是一个回合；回合里每请求模型一次是一轮迭代。
会话 / session一段连续的对话，有唯一的 session_id，记录在 state.db。
流式输出模型边生成边返回，界面上文字一点点出现。
Profile一套独立的配置 + 密钥 + 数据目录。一个网关可同时服务多个 profile，互相隔离。
技能 / Skill一份可复用的操作手册（SKILL.md），告诉 Agent 某类任务怎么做。
插件在不改核心代码的前提下扩展功能（新平台、新模型服务商、新记忆后端…），放在 plugins/。

想读源码：先看根目录 AGENTS.md，再按区域看 agent/AGENTS.md、gateway/AGENTS.md、tools/AGENTS.md。
