先认识几个词

后面的图反复出现这些概念，先有个印象就好。

GatewayOpenClaw 的常驻主进程，默认监听 18789 端口。所有渠道、客户端、agent 都在它里面运行或连接到它。
渠道（Channel）消息进出的地方，比如 Telegram、Discord、Slack。每个渠道是一个插件。
模型提供方（Provider）负责“怎么调用某家模型 API”，比如 anthropic、openai。也是插件。
会话 / 转录会话（session）是一段持续的对话；转录（transcript）是这段对话所有消息的记录，存在 SQLite 里。
回合（turn）用户发一条消息、agent 给出完整回复，这算一个回合。一个回合里可能多次调用模型和工具。
Attempt回合的一次“尝试”。出错重试、切换模型时，同一个回合会有多次 attempt。
Harness执行一次 attempt 的底层引擎。内置的叫 openclaw；插件可以提供别的（如 codex）。
工具（Tool）模型可以调用的能力，比如执行命令、打开浏览器、发消息。模型说“我要调用某工具”，由程序真正执行。
Steer / Follow-upagent 正在忙时又来了新消息：steer 是把它插进正在进行的回合，follow-up 是排队等下一个回合。
压缩（Compaction）对话太长、超出模型上下文窗口时，把旧消息总结成摘要，腾出空间。
回退（Fallback）主模型不可用（限流、认证失败等）时，按配置换备用模型继续。

第 0 部分 · 系统总览

先看大图：谁连到 Gateway，消息从哪进、到哪去。

在新标签页打开 ↗

怎么读这张图

  1. 左上：控制端（网页 Control UI、命令行、手机/电脑 App）通过 WebSocket 连到 Gateway。
  2. 左下：IM 用户在 Telegram 等平台发消息，由对应的渠道插件接收。
  3. 两条入口最终都进入中间的渠道回合 + Auto-reply，这是统一的消息处理管线。
  4. 管线调用 Agent 运行时，它再去调用模型提供方并执行工具。
  5. 会话和转录写入 SQLite。

要点

  • OpenClaw 核心很小，渠道、模型、工具、记忆大多是插件，插件只能通过 openclaw/plugin-sdk/* 与核心交互。
  • Gateway 启动时由 loadGatewayPlugins 加载插件，再由 ChannelManager 启动各渠道账号。
  • 数据库读写在 worker 线程里做，主线程不阻塞。
类比：Gateway 像一家餐厅的前台。渠道是不同的点餐入口（电话、外卖 App、堂食），Auto-reply 是统一的后厨调度，Agent 是厨师，模型 API 是厨师请教的“大脑”，工具是厨房里的各种器具。

第 1 部分 · 一条消息的旅程

以 Telegram 为例，按时间顺序看一条消息怎么变成回复。

在新标签页打开 ↗

逐步讲解

  1. 入站：Telegram 插件用 grammY 库收到消息，调用 runChannelInboundEvent 交给核心。
  2. 记录：渠道回合先调用 recordInboundSession，把“收到一条消息”写进会话存储。
  3. 调度：dispatchInboundMessage 进入 Auto-reply 管线，最终调用 runReplyAgent。
  4. 思考与行动：Agent 流式请求模型；模型可能要求调用工具，执行后把结果交回模型，直到模型给出最终文本。
  5. 回复：回复沿原路返回，由 deliverReply 调用 Telegram Bot API 的 sendText 发给用户。

要点

  • 回复是流式的：模型边生成，渠道边发送分块，用户不用等全部生成完。
  • 发送期间还会并行显示“正在输入…”状态和草稿预览。
  • Control UI 的 chat.send 从 Gateway 进入，汇入同一条 Auto-reply 管线，只是回复通过 WebSocket 事件推回。

第 2 部分 · 回复编排（进入 harness 之前）

放大第 1 部分中间的“Auto-reply”：在真正调用模型之前，OpenClaw 做了哪些判断。

在新标签页打开 ↗

逐步讲解

  1. 渠道调度：渠道把消息交给 getReplyFromConfig，这是回复逻辑的总入口。
  2. 解析上下文：确定由哪个 agent 回复、属于哪个会话、默认用哪个模型、在哪个工作目录运行。
  3. 指令与命令：识别 /model、/think、/queue、/status 等。如果消息只有命令，直接回复结果，不调用模型。
  4. 队列策略：检查这个会话是否正有 agent 在运行。空闲就 run-now；正忙则按配置 steer（插进当前回合，默认）、follow-up（排队）、collect（合并）或 interrupt（打断）。
  5. runReplyAgent：启动“正在输入”状态，建立分块回复管线；必要时先 flush 记忆、预压缩过长的历史。
  6. 模型回退：按“请求的模型 → 配置的备用模型 → 主模型”顺序准备候选，逐个尝试，还可在同一模型下轮换多个 API 凭据。
  7. runEmbeddedAgent：每个候选都要先在“会话 lane”和“全局 lane”排队（控制并发），然后交给 harness（第 3 部分）。
  8. 投递：产生的回复块经 ReplyDispatcher 发回渠道。

要点

  • 同一个会话同一时刻只允许一个回合在跑，保证对话顺序不乱。
  • “会话忙”时默认用 steer：用户的补充消息会被注入正在进行的回合，agent 能在下一次思考时看到。
  • 回退只针对可恢复错误（限流、过载、认证等）；上下文溢出这类错误先走压缩，不直接换模型。

有一个分支图中没画：模型运行时配置为 CLI 后端（如 claude-cli）时，这里会改为启动外部 CLI 进程，见第 3 部分。

第 3 部分 · Harness 分层与选择

回答“harness 层面怎么体现”：谁来真正执行一个回合，是怎么选出来的。

在新标签页打开 ↗

Harness 是什么

  • Harness 是执行一次 attempt 的底层引擎。它不是模型提供方，也不是渠道，也不是工具注册表。
  • 它的契约（AgentHarnessContract）核心只有两个方法：
    supports(ctx)：“这个模型/路由我能不能跑？”
    runAttempt(params)：“跑一次，返回结果。”
  • 输入统一是 AttemptParams（会话、模型、凭据、工具策略、各种流式回调），输出统一是 AttemptResult（终态、文本、工具记录、用量、压缩次数等）。

怎么选

  1. 先看配置里模型级的 agentRuntime.id，再看提供方级。
  2. 没配置（auto）：逐个询问已注册 harness 的 supports()，按优先级选第一个说“能”的。
  3. 都不支持：用内置的 openclaw，它对任何模型都返回“能”。
  4. 插件 harness 一旦接手，失败了也不会偷偷换内置 harness 重跑，避免重复副作用。

三种执行方式

  • 内置 openclaw：在 Gateway 进程内运行 OpenClaw 自己的 agent-core 循环（第 4、5 部分详细展开）。
  • 插件 harness（如 codex）：启动 codex app-server 子进程，通过标准输入输出上的 JSON-RPC 通信。Codex 自己管理线程和压缩；需要 OpenClaw 的工具时，它发回 item/tool/call 请求，由 OpenClaw 执行后回复。
  • CLI 后端（如 claude-cli）：不属于 harness。它在回复编排层就分流了，直接启动外部 CLI 进程，工具通过本地回环 MCP 提供。

核心始终负责

  • 模型与凭据解析、思考等级、上下文预算
  • OpenClaw 转录文件、工作区、沙箱、工具策略
  • 渠道回复回调、模型回退策略
类比：核心是餐厅前台，负责接单、核对忌口、选择厨房。Harness 是厨房，大家都认同一种“点单格式”（AttemptParams）和“出餐格式”（AttemptResult）。内置 openclaw 是自家后厨；codex 是隔壁的加盟厨房，通过对讲机（JSON-RPC）沟通，缺什么食材（工具）就回头找前台要。CLI 后端则是外包的餐饮公司，前台选厨房之前就把单子转给它了。

第 4 部分 · 内置 harness 执行一次 attempt

放大第 3 部分的“内置 harness”：runEmbeddedAttempt 从头到尾做了什么。

在新标签页打开 ↗

逐步讲解

  1. 工作区与沙箱：确定 agent 在哪个目录工作；如果配置了沙箱，就准备 Docker/Podman 环境。
  2. 加载技能：读取技能（skills）快照，技能是一组可复用的说明和脚本。
  3. 组装工具：核心工具（执行命令、读写文件等）、插件工具（如浏览器）、MCP/LSP 工具，再建立工具目录。
  4. 构建系统提示词：把工作区上下文文件、技能说明、工具说明拼成发给模型的“角色设定”。
  5. 打开转录、建会话：从 SQLite 打开这段对话的历史，创建 AgentSession（包着 agent-core 的 Agent）。
  6. 组装历史上下文：上下文引擎决定带哪些历史消息给模型，避免超出窗口。
  7. 订阅事件流：先订阅 agent 的事件，把文本增量切成块实时发给渠道。先订阅再提交，才不会漏掉开头的输出。
  8. 提交 prompt、等待结算：调用 activeSession.prompt()，agent 循环开始运行（第 5 部分），等它结束、事件全部处理完。
  9. 返回 AttemptResult：打包终态（成功/中止/超时/失败）、回复文本、工具记录和用量。
  10. finally 清理：不管成功失败，都会清理会话、注册过的工具和技能环境变量。

要点

  • 前 4 步是“准备能力”：决定这次模型能看到什么、能做什么。
  • 第 5～7 步是“建立会话”：把历史和实时输出通道接好。
  • 真正的“思考—行动”循环发生在第 8 步里面，下一张图展开。
  • 每一步都包在 prepare("attempt.xxx") 里计时，方便诊断哪一步慢。

第 5 部分 · Agent 循环一次完整运行

放大第 4 部分的“提交 prompt”：模型调用、工具调用怎么一轮轮交替进行。

在新标签页打开 ↗

逐步讲解

  1. 发起：runner 调用 AgentSession.prompt(text)。AgentSession 先跑扩展钩子、检查是否需要压缩，再把文本包装成 UserMessage 交给 Agent.prompt。用户消息同时写入 SQLite。
  2. 第一轮模型调用：Agent 把“系统提示词 + 历史消息 + 工具定义”打包成 Context，调用 streamSimple。
  3. 选适配器：packages/ai 根据模型的 api 字段（如 anthropic-messages）找到对应适配器，发起 HTTP 流式请求。
  4. 流式返回：模型以 SSE 流返回增量；适配器把它们转成统一的事件（text、thinking、toolcall、done）。
  5. 边收边发：Agent 把增量拼成 AssistantMessage，同时发出 message_update 事件，runner 据此把文本分块发给用户。
  6. 工具调用：如果模型停在 stopReason=toolUse，Agent 取出工具调用，先按 JSON Schema 校验参数，再执行（默认并行），得到 ToolResult。
  7. 持久化：每条消息结束（message_end）时，AgentSession 把助手消息和工具结果写入 SQLite。
  8. 下一轮：工具结果追加进上下文，再调一次模型。如此循环。
  9. 结束：模型返回 stopReason=stop、且没有排队的 steer/follow-up 消息时，发出 agent_end。AgentSession 再检查是否需要压缩或重试，然后结算。

要点

  • 一“轮”（turn）= 一次模型调用 + 可能的工具执行。一个回合可能包含很多轮。
  • 循环没有最大轮数限制。结束条件是：没有更多工具要执行、出错、被中止、钩子要求停止，或工具循环检测判定陷入死循环。
  • 参数校验失败不会让程序崩溃，而是作为错误结果返回给模型，让它自己修正。
  • steer 消息在“检查点”被注入：每轮开始前、工具执行间隙都会检查。

第 6 部分 · Agent 内部数据流

换个角度，只看数据：信息从哪来、在哪拼装、最后流向哪里。

在新标签页打开 ↗

五个阶段

  1. 输入：工具定义（每个工具的名字、说明、参数 JSON Schema）、用户消息、系统提示词、历史转录。
  2. 组装：工具和用户消息进入 AgentState（agent 的内存状态：messages、tools、model、思考等级）。convertToLlm 把内部消息（包括压缩摘要、分支摘要等自定义类型）转换成模型认识的格式，加上系统提示词和历史，得到 LLM Context。
  3. 模型调用：provider 适配器把 Context 翻译成对应厂商的请求格式，发出流式请求，把响应翻译回统一事件。
  4. 输出：事件被拼成 AssistantMessage，里面可以有文本、思考过程和工具调用。有工具调用就进入“工具执行”，结果（ToolResult）追加回 AgentState，开始下一轮。
  5. 落地：文本增量实时发往渠道；每条完整消息都写入 SQLite 转录。

核心数据结构

  • UserMessage：{role:"user", content:[文本, 图片…]}
  • AssistantMessage：content 可含 text / thinking / toolCall，另带 provider、model、usage、stopReason。
  • ToolResultMessage：{role:"toolResult", toolCallId, toolName, content, isError}
  • stopReason 取值：stop（正常结束）、toolUse（要调工具）、length（超长）、error、aborted。

这是一个闭环：本次写入 SQLite 的转录，就是下次对话时“历史转录”的输入。

第 7 部分 · 一次回复运行的生命周期

从状态的角度看：一次运行会经历哪些状态，出错时如何恢复，最后以什么结束。

在新标签页打开 ↗

正常路径

  1. 排队中（queued）：运行被创建，等待开始。
  2. 预压缩：历史太长时，先 flush 记忆、压缩上下文（memory_flushing / preflight_compacting）。
  3. 运行中（running）：run-loop 反复派发 attempt。全局并发满时进入“等待全局 lane”，拿到容量再继续。
  4. 结算回复：记录用量、生成最终回复内容。
  5. 已完成（completed）。

出错时怎么办

  • 瞬时错误（网络抖动、限流）：退避后重试，或轮换 API 凭据，或降低思考等级。
  • 上下文溢出：压缩历史后重试，最多 3 次；还不行就截断过长的工具结果。
  • 不可恢复（凭据全部失效、持续过载）：抛出 FailoverError，换下一个候选模型。
  • 终态：所有候选都失败或运行卡死 → 失败；用户中止或被新运行替代 → 已中止（任何阶段都可能发生）。

“排队中、预压缩、运行中、等待 lane、已完成、失败、已中止”是代码里 ReplyOperationPhase 的真实状态；“重试、压缩上下文、切换备用模型”是 run-loop 内部的恢复分支，不是枚举值。
