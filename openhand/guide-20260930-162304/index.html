先看全局：谁负责什么

OpenHands 仓库（Agent Canvas 前端）+ software-agent-sdk 仓库（Agent Server / SDK）

打个比方：Canvas 是遥控器加显示屏，Agent Server 是干活的工人，LLM 是工人的大脑，工作目录是工人的工位。遥控器只负责下指令、看直播，真正的活全在服务端干。
  1. Agent Canvas（本仓库）：React 前端，负责界面、选择连哪个后端、把用户输入发出去、把事件画出来。它不自己实现 Agent 逻辑。
  2. Agent Server（Python，另一个仓库）：接收请求，创建会话，运行 Agent 循环，调用 LLM，在本机执行终端命令和改文件。
  3. Ingress（:8000）：本地的统一入口，按路径把请求分给 Agent Server、Automation 或静态前端，浏览器只需要认一个地址。
  4. 两种通信方式：REST 用来“办手续”（创建会话、读历史、暂停），WebSocket 用来“看直播”（实时推送事件、发送消息）。

一条消息的完整旅程

把下面的流程串起来看

你在首页输入“帮我修复这个 bug”并回车后，会依次经过：

③ 前端打包配置，发起创建会话
④ 服务端建目录、建 Agent，首条消息开跑
⑤ 前端跳到会话页，拉历史、连 WebSocket
⑥⑦ 服务端循环：问 LLM → 调工具 → 看结果
⑧ 服务端每个事件落盘后推送
⑨ 前端收到事件，画成聊天卡片
⑩ 状态RUNNING → FINISHED，按钮随之变化

① 本地栈启动流程

bin/agent-canvas.mjs · scripts/dev-with-automation.mjs · electron/main.mjs

一句话：一条 npx @openhands/agent-canvas 命令（或打开桌面版），在你电脑上依次拉起 4 个进程，最后打开 http://localhost:8000。
  1. 执行启动命令：命令行版和 Electron 桌面版最终都调用同一个 main()，只是桌面版多一个显示启动日志的加载窗口。
  2. 检查环境：确认装了 uvx（用来运行 Python 包）和 npm，并确认 8000 / 18000 / 18001 / 3001 端口空闲，被占用就立即报错。
  3. 生成配置：从 config/defaults.json 读取版本和端口，生成或读取 Session API Key（保存在 ~/.openhands/agent-canvas/api-key.txt），后续所有请求都要带上它。
  4. 启动 Agent Server：用 uvx 按锁定版本安装并运行 Python 服务，每 500ms 轮询一次 /server_info，直到服务就绪。
  5. 启动 Automation：先把自动化密钥写进 Agent Server，再启动定时任务服务（数据存在 SQLite）。
  6. 启动静态前端和 Ingress：静态服务器把 API Key 注入页面，Ingress 按“最长前缀”规则分发请求。
  7. 打开页面：浏览器或桌面窗口加载 :8000。按 Ctrl+C 或关窗时，给所有子进程发 SIGTERM，3 秒后还没退出的强制 SIGKILL。

② 前端启动与后端选择

src/entry.client.tsx · src/api/backend-registry/ · src/root.tsx

一句话：页面加载后先决定“连哪个后端”，再确认这个后端能用、版本够新，最后才把界面画出来。
  1. entry.client：等多语言文案加载完，再把 React 挂到页面上。
  2. Provider 栈：从外到内依次套上多语言、数据缓存（TanStack Query）、当前后端、埋点。所有页面都能通过它们拿到这些公共能力。
  3. 读取已存后端：后端列表存在浏览器 localStorage。第一次打开时自动生成一个 default-local，地址就是当前页面，Key 是启动器注入的那个。
  4. 选出活动后端：优先级依次是 URL 里指定的、上次选的、健康的本地后端。后端可以是 local（本机 Agent Server）或 cloud（OpenHands 云）。
  5. 探测 server_info：请求 /server_info（5 秒超时），检查 Agent Server 版本不低于 1.47.0。
  6. 分支：401 表示 Key 不对，显示“输入 API Key”画面；连不上或版本太低，显示“后端不可用”画面；通过则进入主界面。

③ 创建会话：本地与云端两条路（前端视角）

home-chat-launcher.tsx · use-create-conversation.ts · agent-server-conversation-service.api.ts · agent-server-adapter.ts

一句话：“创建会话”就是把 Agent 的全部配置（用哪个 LLM、有哪些工具、在哪个目录干活、第一句话是什么）打成一个包，交给后端。
  1. 首页输入任务：可以附带仓库、本地目录、插件，还没配置 LLM 时会拦住。
  2. useCreateConversation：决定用哪个 Agent Profile；某些情况下回退为直接发送完整的 agent_settings。
  3. 看后端类型：本地和云端从这里分开走。
  4. 本地：准备工作目录：默认每个会话一个独立目录（可以是 git worktree）；如果 Agent Server 跑在 Docker 里，就用容器内的 /workspace。
  5. 本地：组装启动请求：包含 LLM 配置（开启流式）、工具（terminal / file_editor / task_tracker…）、技能、首条消息（带 run:true）、最多 500 步、卡死检测、确认策略。密钥只传“去哪取”的地址，不传明文。
  6. 本地：POST 创建会话：Agent Server 立刻返回会话 id，状态直接是 READY。
  7. 云端：先返回一个 task-xxx，云端要分配沙箱、克隆仓库、装技能，前端每 3 秒轮询一次，READY 后把地址栏换成真实 id。

④ 服务端创建会话（Agent Server 内部）

software-agent-sdk：conversation_router.py · conversation_service.py · event_service.py

一句话：服务端把收到的 JSON 还原成真正的 Agent 对象，建好会话目录和运行时，把第一句话塞进去开跑，然后马上返回，Agent 在后台继续执行。
  1. POST /api/conversations：所有 /api 接口统一校验 Session API Key。
  2. 还原请求对象：用 Pydantic 把 JSON 变回 Agent（含 LLM 和工具清单）、工作区、确认策略等对象。
  3. 调整 Agent：加载技能，追加系统提示，按需切换到 git worktree，注册前端提供的“客户端工具”。
  4. EventService.start：创建工作目录并 git init，建立 LocalConversation（真正运行 Agent 循环的对象），同时在磁盘上建 base_state.json 和 events/ 目录。
  5. 挂上订阅者：自动起标题、遥测、Webhook 等，都会收到之后的每一个事件；同时写 meta.json。
  6. 发送首条消息：调用 send_message(run=True)，后台循环开跑。
  7. 返回 ConversationInfo：新建返回 201，同 id 已存在返回 200。

⑤ 打开会话：预加载历史 + 建立 WebSocket

conversation.tsx · use-conversation-history.ts · conversation-websocket-context.tsx · use-websocket.ts

一句话：先用 REST 把“以前发生过什么”拉下来显示，再打开 WebSocket 看“接下来发生什么”。after_seq 相当于书签，告诉服务端“我已经看到第几条了”。
  1. 拿会话信息：useActiveConversation 请求会话详情，拿到 conversation_url 和 key。还没拿到地址时每 3 秒刷新一次，之后每 30 秒一次。
  2. REST 预加载历史：先查事件总数，再取最新 50 条，倒过来变成时间正序后放进事件 Store。书签 afterSeq = 总数 − 1。往上滚动时再加载更早的记录。
  3. 建立 WebSocket：历史加载完才开始连接。地址是 /sockets/session/:id?after_seq=N，连上后第一帧发送 {type:"auth"} 鉴权（Key 不放在 URL 里），服务端补发 seq > N 的事件。
  4. 断线重连：按 1s、2s、4s… 最长 30s 的间隔自动重连（带随机抖动），每次都带最新书签，只补漏掉的事件。Store 按 id 去重，不会出现重复消息。

⑥ 发一条消息后，服务端怎么跑

session_socket.py · event_service.py · local_conversation.py · agent.py · llm.py

一句话：消息先变成一个事件存起来，然后唤醒后台循环。循环每一步都是：把历史给 LLM 看，LLM 说“调用某个工具”，执行它，把结果记下来，再进入下一步。
  1. 收到消息：前端经 WebSocket 发送 {role:"user", content}，会话 Socket 交给 EventService。
  2. 写入 MessageEvent：用户消息成为一条正式事件。如果会话之前是 FINISHED，会被重置为 IDLE。
  3. 后台 arun()：以异步任务运行，接口不阻塞。如果已经在运行，就先记下来，这一轮跑完再跑一轮。
  4. 循环：astep：Agent 把历史整理成对话发给 LLM，LLM 返回要调用的工具（tool_calls），生成 ActionEvent；执行工具得到 Observation，生成 ObservationEvent。每个事件都先落盘，再推送给前端。
  5. 结束：Agent 调用 Finish 工具或直接回复文字时变为 FINISHED；EventService 推送一帧 full_state，前端据此更新状态。
一个容易误解的细节：前端在 WebSocket 消息里带了 run:true，但服务端解析时会丢弃这个字段，每条 WS 消息都会触发运行。只有 REST 接口 POST /events 会认 run。

⑦ Agent 的一步（step）里发生了什么

openhands-sdk/openhands/sdk/agent/agent.py · response_dispatch.py

一句话：一步 = 整理记忆 → 问大脑“下一步做什么” → 动手做。做完的结果成为新记忆，下一步大脑就能看到。
  1. 读取事件视图：从会话状态中取出到目前为止的所有事件。
  2. 事件 → LLM 消息：把系统提示、用户消息、之前的动作和结果，转换成 LLM 能读懂的对话格式。如果太长，先触发“上下文压缩”（生成 Condensation 事件，本步结束，下一步用压缩后的上下文继续）。
  3. LLM 生成：连同工具定义一起发给 LLM（经 litellm，失败自动重试最多 5 次）。上下文超长等错误会请求压缩后再试。
  4. 看回复类型：如果是纯文字，说明 LLM 认为可以直接回答用户，生成 MessageEvent 并标记 FINISHED；如果是工具调用，继续往下走。
  5. 生成 ActionEvent：解析参数，找到对应的工具。工具名不存在或参数不合法时，生成 AgentErrorEvent 回给 LLM，让它自己修正。
  6. 风险确认闸门：安全分析器评估风险，确认策略决定是否要人工确认。需要确认就进入 WAITING_FOR_CONFIRMATION 暂停；用户拒绝会生成 UserRejectObservation。
  7. 执行工具：在本机执行（终端命令在 tmux 里跑，文件编辑直接改工作目录），结果包装成 ObservationEvent。如果执行的是 Finish 工具，就标记 FINISHED。

⑧ 事件的一生：产生 → 落盘 → 广播

local_conversation.py · event_store.py · pub_sub.py · session_socket.py

一句话：每个事件先写成磁盘上的一个 JSON 文件，写成功后才通知订阅者。所以前端即使断线，也总能从磁盘把漏掉的补回来。
  1. 产生：Agent 或会话每产生一个事件（消息、动作、结果、状态变化），都经过同一条回调链。
  2. 先写磁盘：EventLog 加文件锁，写入 events/event-00001-<id>.json，每个事件都有递增的序号 seq。状态字段一变化，base_state.json 也会自动保存。
  3. 再广播：AsyncCallbackWrapper 把事件从 Agent 线程安全地转交给服务端的事件循环，PubSub 并发通知所有订阅者，一个订阅者出错不会影响其他订阅者。
  4. 订阅者：内部订阅者负责起标题、发 Webhook、遥测；会话 Socket 把事件包成 DurableFrame(seq) 发给前端。
  5. 打字机效果：LLM 流式吐出的 token 走另一条“流式进度广播”，不落盘，前端收到的是 ItemStarted / Delta 帧；正式事件到达后，前端按 id 收起这些临时片段。

⑨ 事件回到前端：分拣、存储、渲染

conversation-websocket-context.tsx · use-event-store.ts · handle-event-for-ui.ts · messages.tsx

一句话：前端收到的每一帧先分类：流式文字进缓冲区，正式事件进 Store，同时触发界面副作用（刷新终端、文件树、状态按钮）。聊天区只渲染加工后的列表。
  1. routeSessionFrame：按帧类型分流。delta 进缓冲区；durable 推进书签后作为正式事件；error 显示错误横幅，但连接保持。
  2. 增量批处理：流式文字每个动画帧只合并提交一次，避免逐字触发渲染导致卡顿。
  3. 事件 Store：按 id 去重，按时间排序，同时保存原始列表 events 和展示列表 uiEvents。
  4. 副作用分发：命令事件写进终端面板，浏览器截图显示到浏览器面板，改文件时刷新 diff 缓存，状态事件写进会话状态 Store。
  5. handleEventForUI：工具结果（Observation）替换对应的动作卡片，正式消息替换流式临时槽，Think / Finish 的结果被隐藏。
  6. 渲染：过滤掉不需要展示的事件，把连续的工具调用折叠成一组，再按事件类型选用对应组件（用户消息、Agent 回复、命令卡片、错误等）。

⑩ 会话执行状态的生命周期

openhands-sdk/.../conversation/state.py · local_conversation.py；前端 use-agent-state.ts

一句话：每个会话都有一个执行状态，它决定界面上显示“停止”“继续”还是“确认/拒绝”按钮。
  1. IDLE → RUNNING：收到消息并调用 run()。
  2. RUNNING → FINISHED：调用了 Finish 工具，或 LLM 直接回复了文字。之后发新消息会重置为 IDLE，再开始新一轮。
  3. RUNNING → WAITING：有动作需要人工确认。接受后回到 RUNNING 并执行这个动作，拒绝则回到 IDLE。
  4. RUNNING → PAUSED：用户点了停止（本地后端调用 interrupt，会取消正在进行的 LLM 请求）。点“继续”回到 RUNNING。
  5. RUNNING → ERROR / STUCK：出现异常、超过 500 步或预算上限，或者卡死检测发现在重复同样的动作。再次 run() 可以恢复。

名词表

会话 Conversation
一次任务的完整上下文：配置、工作目录、所有事件。磁盘上对应 conversations/<id>/。
事件 Event
会话里发生的每一件事，都记录为一个事件，不可修改，按顺序编号（seq）。
MessageEvent
一条消息，来自用户、Agent 或环境。
ActionEvent
Agent 决定调用某个工具，比如“执行命令 ls”。
ObservationEvent
工具执行的结果，比如命令输出。通过 action_id 和对应的动作关联。
ConversationStateUpdateEvent
状态同步，比如 execution_status 变为 running，或 token 用量统计。
Condensation
上下文太长时，把早期事件“遗忘”并换成摘要，让 LLM 不超出窗口限制。
工具 Tool
Agent 能动手的方式：terminal、file_editor、task_tracker、browser，以及内置的 think、finish。
Session API Key
本地 Agent Server 的访问口令，REST 放在请求头 X-Session-API-Key，WebSocket 放在第一帧。
seq / after_seq
事件序号 / 客户端书签，用于断线续传。
DurableFrame / Delta
WebSocket 帧：前者是已落盘的正式事件，后者是流式文字片段（不落盘）。
Ingress
本地统一入口（:8000），按路径前缀把请求转发给各个服务。
